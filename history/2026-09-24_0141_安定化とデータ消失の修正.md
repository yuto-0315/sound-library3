## 3. 見つかった原因と修正

### 3.1 データが消える問題

| # | 症状 | 原因 | 修正 |
|:--|:--|:--|:--|
| D1 | **ページを移動して戻るとタイムラインが消える**（報告された症状） | DAW を開いた直後、保存済みの作業内容を非同期で読み込んでいる**間に**、自動保存の effect が初期状態（空のトラック 1 つ）を `localStorage` に書き込んでいた。その後の読み込みでは、今書かれた空のデータが読まれていた | 読み込みが終わるまで自動保存しない（`isProjectLoaded`）。読み込みに失敗した場合も、空の状態で上書きしないよう自動保存を止める |
| D2 | 音をたくさん置くと、再読み込みで作業内容が消える | 自動保存先が `localStorage`（約 5MB）で、クリップごとに音声データ（base64）を丸ごと保存していたため、すぐ容量を超えて保存に失敗していた（エラーはコンソールに出るだけ） | 自動保存を **IndexedDB** に移動。音声データは 1 回だけ保存する形式（v2）にした。旧データは自動で移行 |
| D3 | 先生ページから楽曲を開くと、もともとあった音素材が消える | 取り込んだ音素材に「既存の最大 ID + 1」を振っていたが、読み込みが終わる前は既存一覧が空のため ID が 1, 2… になり、**既存の録音を上書きしていた** | ID は IndexedDB に自動採番させる（`addRecording` / `addRecordings`） |
| D4 | 保存したはずの録音が消えていることがある | IndexedDB の書き込みを、リクエストの `onsuccess` で成功扱いにしていた。実際の書き込み確定（`complete`）前なので、容量不足などで中断されても「保存済み」に見えていた | すべての処理をトランザクションの `complete` まで待ってから成功を返す（`runTransaction`） |
| D5 | 旧データの移行で録音が消える | 移行時に「名前が同じなら同じ録音」と判定していたため、同じ名前の別の録音（例: たいこ が 2 つ）は片方が捨てられ、その後 localStorage も消されていた | 名前・作成日時・音声データで判定し、全件の書き込み確定後に、移行した分だけ localStorage から消す |
| D6 | 共有ページで「音ライブラリーに追加」すると失敗しやすい | ダウンロードした音声を容量の小さい localStorage に保存していた | IndexedDB に保存。同じ音声の二重追加も防止 |
| D7 | 録音一覧の音が途中で再生できなくなる | 後片付けの effect が「録音一覧が変わるたび」に実行され、表示中の音の URL まで解放していた | 後片付けはアンマウント時だけにした |
| D8 | 読み込み失敗後に「リセット」で保存データが消える（レビューで発見） | 失敗時の案内が「リセットを押して」となっており、リセットは読めなかったデータを削除していた | 「もう一度読み込む」ボタンと、閉じられない「自動保存停止中」表示を追加。リセットは作業内容をバックアップしてから行い、バックアップできなければ中止する |
| D9 | 先生ページから開いた楽曲で、端末の作業内容が黙って置き換わる（レビューで発見） | 確認なしで置き換え、しかも「取り込み → 削除 → 自動保存」が別々の処理だった | 作業内容があれば確認。「バックアップ → 自動保存に書く → 取り込み元を削除」を 1 つのトランザクションで行う |
| D10 | 名前を付ける前に別のページへ行くと、録音が消える（レビューで発見） | 保存前の録音はページの state にしか無かった | アプリを開いている間は一時的に覚えておき、戻ったときに復元する（`utils/unsavedDraft.js`）。新しく録音するときは確認する |
| D11 | 自動保存に 1 回失敗した後、何もせず移動すると保存されない（レビューで発見） | 失敗時に「保存待ち」の印を戻していなかった | 失敗時は保存待ちに戻し、ページを離れるときに再保存する |
| D12 | DAW を 2 つのタブで開くと、古いタブが新しい内容を上書きする（レビューで発見） | タブに戻ったときに作業内容を読み直していなかった | タブに戻ったとき、より新しい保存があれば読み込み直す |
| D13 | Safari がしばらく使わないサイトのデータを消す | Safari は一定期間操作されないサイトの保存データを削除することがある | 起動時に `navigator.storage.persist()` で永続化を依頼 |
| D14 | リセットや先生の楽曲で置き換えた作業内容を戻せない（2 周目で発見） | バックアップは取っていたが、画面から戻す手段が無く、空の作業内容で上書きされることもあった | 「1つ前の作業に戻す」ボタンを追加（押すたびに入れ替わる）。クリップのある作業内容だけをバックアップする |
| D15 | プロジェクトファイルを読み込むと、今の作業内容が確認なしに置き換わる（2 周目で発見） | 読み込み失敗で自動保存が止まっている場合も、読めなかったデータを上書きしていた | 確認し、バックアップしてから置き換える |
| D16 | 旧バージョンの作業内容（localStorage）しか無い端末で、先生の楽曲を開くと旧データが消える（2 周目で発見） | 「今の作業内容があるか」を IndexedDB だけで判定し、その後の保存で旧データを削除していた | 旧データも作業内容として扱って確認・バックアップし、移行かバックアップが済むまで消さない |
| D17 | 別タブの内容を読み込み直している間の編集が消える（2 周目で発見） | 読み込みを待つ前後で、このタブで編集したかを確認していなかった | 読み込みの前後で編集が無いことを確認してから置き換える |
| D18 | 保存中に次の録音をして、先の保存が失敗するとその音が消える／保存中にページを離れて失敗すると消える（2 周目で発見） | 保存中でも次の録音ができ、失敗時に一時保管していなかった | 保存中は録音・ファイル選択を無効化。失敗時はページを離れていても一時保管し、入力途中の名前・タグも戻す |

### 3.2 一部の iPad で使えない・動作が不安定な問題

| # | 症状 | 原因 | 修正 |
|:--|:--|:--|:--|
| I1 | iPad で録音した音が再生できない（`NotSupportedError`） | iPad の録音は mp4 なのに、Blob・Data URL・アップロード時のファイル名をすべて **audio/wav** と表記していた | 実際の録音形式で保存。**中身（先頭バイト）から形式を判定**して表記を直す処理を追加し、保存済みの誤ったデータも読み込み時に直す |
| I2 | PC で録音して共有した音が古い iPad で鳴らない | Chrome は `audio/mp4` だけ指定すると中身が Opus になる | 録音形式の第一候補を `audio/mp4;codecs=mp4a.40.2`（AAC）にした |
| I3 | 古い iPad（iPadOS 14.0 以前）で DAW の音が出ない・長さが取れない | `Blob.arrayBuffer()`、Promise 版 `decodeAudioData`、`new AudioContext({ sampleRate })` など古い Safari に無い API を使っていた | FileReader による代替、コールバック版の併用、オプション無しの AudioContext に変更 |
| I4 | iPad で再生のタイミングがずれる・停止後に鳴る・鳴らない | クリップごとに `<audio>` を作って `setTimeout` で再生していた（読み込み待ちで遅れる、停止しても待ち中の音が後から鳴る、iOS の自動再生制限にかかる） | **Web Audio API** で事前にデコードし、AudioContext の時計で予約する方式に変更。停止・移動時は予約中の音も確実に止める |
| I5 | 消音スイッチ（マナーモード）がオンの iPad で DAW が無音 | Web Audio は消音スイッチに従う | iOS 17 以降は `audioSession`、それ以前は無音の `<audio>` をループ再生して回避。※最初の実装では開始直後に自分で解除してしまう不具合があり、レビューで発見して修正 |
| I6 | 一部の iPad で IndexedDB を開けず、読み込み中のまま止まる | Safari 14.1〜15 の「読み込み直後の `indexedDB.open` が応答しない」不具合、ほかのタブによるアップグレードのブロック | `indexedDB.databases()` を使った回避策、タイムアウト、`onversionchange` での接続解放を追加 |
| I7 | 古い iPad で名前やタグを入力できない | タッチ端末向けの CSS が**全ページの入力欄にも** `user-select: none` をかけていた（本番ビルドでは全 CSS が 1 つにまとまるため、DAW ページ用の指定が全ページに効いていた） | DAW ページ内だけに限定し、入力欄は選択可能に戻した |
| I8 | タッチでドラッグするとページが先頭に飛ぶ・画面がスクロールできなくなる | ドラッグ中に `body` を `position: fixed` にしていた。`touchcancel` の処理が無く、割り込まれると固定されたままになっていた | `position: fixed` をやめ、`passive: false` のリスナーで `preventDefault` してスクロールを止める（`hooks/useTouchDrag.js`）。`touchcancel` も処理 |
| I9 | 縦向きの狭い iPad で音素材リストをスクロールできない（レビューで発見） | 幅 768px 以下ではリストが横並びになるのに、横方向の動きをドラッグとして扱っていた | 横並びのときは横をスクロール、縦（タイムラインの方向）をドラッグにする。音素材に「つまみ」を付け、つまみからはどの方向にもドラッグできる |
| I10 | 再生中に全体がカクつく | 再生中、毎フレーム state を更新して画面全体を描き直していた | プレイヘッドは DOM を直接動かし、React の再描画を通さない |
| I11 | 先生ページの「DAWで開く」が iPad で開かない | データの取得を待ってから `window.open` していたため、ポップアップとしてブロックされていた | クリック直後に空のタブを開いておき、準備ができたらそのタブで表示する |
| I12 | 共有ページの音声を iPad で再生できない | 取得を待ってから `play()` していたため、タップの扱いが切れて再生が拒否されていた | タップ直後に `<audio>` 要素の再生許可を取り、その要素を使い回す |
| I13 | 先生ページの音声プレーヤーが iPad Safari で再生できない | `download.php` が Range リクエストに対応していなかった（Safari の `<audio>` は対応していないサーバーの音声を再生しない） | 206 / 416 / HEAD に対応。保存済みファイルの中身から Content-Type を判定 |

## 4. データの保存形式・保存先の変更

### IndexedDB（`SoundLibraryDB`、バージョン 2 のまま）

| ストア | キー | 内容 |
|:--|:--|:--|
| `recordings` | 自動採番 | 録音した音（`audioData` は中身に合った MIME の Data URL） |
| `songs` | `daw-autosave` | DAW の自動保存（**新規**。以前は localStorage の `dawProjectAutoSave`） |
| `songs` | `daw-autosave-backup` | リセット・楽曲の取り込み・ファイル読み込み前の作業内容（**新規**。1 つだけ残す。「1つ前の作業に戻す」で入れ替え） |
| `songs` | `daw-import-song` | 先生ページから DAW へ渡す楽曲（従来どおり） |

- スキーマのバージョンは変えていないので、既存の端末のデータはそのまま使える
- 旧形式の localStorage（`soundRecordings`、`dawProjectAutoSave`、`daw-import-song`）は自動で移行し、移行が確定してから消す

### プロジェクト（タイムライン）の形式 v2（`utils/project.js`）

- v1: 各クリップの `soundData.audioData` に音声を丸ごと埋め込んでいた（同じ音を 10 回置くと 10 回分）
- v2: 音声は `assets` に 1 回だけ保存し、クリップは `audioRef` で参照する
- 読み込みは v1 / v2 の両方に対応（先生ページに保存済みの過去の楽曲も開ける）
- 自動保存・クラウド保存は「使っている音だけ」、プロジェクトファイルは「音素材ライブラリも含めて」保存する

### バックアップの復元

音楽づくりページの「1つ前の作業に戻す」ボタン（バックアップがあるときだけ表示）で、今の作業内容とバックアップを入れ替える。もう一度押すと元に戻る。バックアップは 1 つだけで、クリップのある作業内容を置き換えたときにだけ更新される。

### 10.5 `node_modules` を履歴から消す（実行前に停止）

- 調べたこと
  - `node_modules` は最初のコミット（`2b7b00b0`）から入っており、**すべてのコミットが書き換わる**
  - GitHub 上のリポジトリ（約 86MB）のほとんどが `node_modules`（28,908 ファイル、git が圧縮して保存している大きさで 約 83MB）。ほかの生成物は合わせて 0.3MB 程度。次に大きいのは `20240329_introduction_to_weba11y.pdf`（11MB、資料なので対象外）
  - リポジトリにアクセスできるのは yuto-0315 だけで、フォークは無い。main にブランチ保護は無い。GitHub Pages は使っていない（`docs/` は別の方法で公開している）
  - `git filter-repo` は入っていないので、git に付属の `git filter-branch` で行う予定だった
- 止めた理由
  - 書き換えには main と PR のブランチへの **force push** が必要で、取り消しにくい
  - 自動モードの安全確認で「破壊的な git 操作」として止められた（事前のバックアップ作成の段階）。回避はせず、依頼者の判断に委ねることにした
- 実行する場合の手順（依頼者が自分で実行する）
  1. PR #1 を先にマージしておく（書き換え後に PR の差分が崩れないように）
  2. バックアップを取る: `git bundle create ../sound-library3-backup.bundle --all`
  3. 書き換える（`git filter-repo` を入れられるならそちらの方が速く安全）
     ```bash
     git checkout main && git pull
     FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch --index-filter 'git rm -r -q --cached --ignore-unmatch -- node_modules build coverage playwright-report test-results' --prune-empty -- --branches
     ```
  4. 最新の内容が変わっていないことを確かめる: `git diff refs/original/refs/heads/main main --stat`（`node_modules` などの削除だけが出る。今回のブランチをマージした後なら何も出ない）
  5. `git push --force-with-lease origin main`（残っているブランチも同様）
  6. 本番サーバーが `git pull` で更新している場合、書き換え後の `git pull` は失敗する（または古い履歴と混ざる）。サーバーでは `git fetch origin && git reset --hard origin/main` か、クローンし直す
  7. GitHub 上の古いコミットは、しばらく URL を直接指定すれば見える状態で残る。完全に消すには GitHub のサポートへの依頼が必要
